## Why this cutover is required

REAL issue #159 first exposed DEF-0073 when the receiver rejected its valid
3.0.1 admission under a newer receiver implementation. Published 3.0.2 repaired
that split-release compatibility boundary and source routing was advanced to
3.0.2.

The subsequent unchanged retry preserved #159's original trusted 3.0.1
admission, delivery ID, and correlation identity. That recovery state exposed
DEF-0086 because the 3.0.2 router could not reuse the predecessor admission
under the newer release.

Published 3.0.3 repairs cross-release admission reuse while keeping exact
same-release reuse unconditional. Predecessor reuse remains target-bound,
requires an exact stable delivery/source/target binding, and must be within the
pinned receiver compatibility policy. The reviewed 3.0.3 path accepts
`ai-sdlc-v3.0.1`, `ai-sdlc-v3.0.2`, and `ai-sdlc-v3.0.3` admissions.

## Reconciliation compatibility during cutover

New admissions use the 3.0.3 router after this change. The source-owned
missing-result reconciliation workflow loads the immutable 3.0.3 trust policy
and accepts only the explicit reviewed admission-release set
`{ai-sdlc-v3.0.1, ai-sdlc-v3.0.2, ai-sdlc-v3.0.3}`.

This preserves issue #159's original 3.0.1 durable admission, preserves recovery
for 3.0.2 admissions, and supports missing-result recovery for new 3.0.3
admissions. Any other admission release remains fail-closed. The accepted set is
static workflow policy, not an operator input.

Do not rewrite #159's admission marker, issue body, delivery ID, or correlation
ID to 3.0.3. Its logical delivery remains
`task-b72eaf2503fc3d27c82f8921e8cfbfff`.
